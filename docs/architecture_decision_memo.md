# Architecture Decision Memo

**Which architecture would I ship—and why?** Ship **Single Agent as the default**, with Staged Two-Agent retained as an experimental audit-oriented option.

**Evidence.** The current `evaluation/benchmark_results.json` contains 20 successful rows: both architectures passed all 10 shared edge cases, including missing information, catalog overlap, expired compliance, PII, prompt injection, budget overrun, and unavailable vendor-risk evidence. In the committed artifact, Single Agent averaged **1.47 ms**, **2 LLM calls**, and **1 tool call** per case. Staged averaged **0.76 ms**, **3 LLM calls**, and **1 tool call**. The artifact is explicitly marked `offline_stub`; these are local orchestration timings, not live provider latency. A live Groq run was attempted with the configured key but did not complete within the bounded run, so no unsupported live-performance claim is made.

**Decision rationale.** Single Agent has one fewer model call and a smaller failure surface. Both paths now apply deterministic policy floors after model output, but Staged still adds an Analyst-to-Reviewer handoff whose correctness depends on the evidence pack and request-derived fallback context. Staged remains useful for audit experiments because the typed handoff is inspectable, but it should not be the shipping default until repeated live-provider runs demonstrate equal or better correctness and latency.

**Tradeoff and guardrails.** The offline fixture contains 20 passing rows, but its 1.47 ms/0.75 ms timings are orchestration overhead, not provider latency, and the suite has only 10 cases. Live evaluation must be repeated with model/date/git metadata, rate-limit retries, per-case outcomes, tool counts, and provider latency before making a stronger architecture claim. Both paths use 10-iteration caps, deterministic Pandas-backed tools, sanitized messages, Pydantic validation, JSON-mode final calls, fail-closed policy reconciliation, and human approval.
